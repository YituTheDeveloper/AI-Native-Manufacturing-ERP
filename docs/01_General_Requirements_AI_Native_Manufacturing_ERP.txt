AI-Native Manufacturing ERP
General Project Requirements, Product Scope, Architecture Principles & AI-Agent Master Instructions

1. Project Vision
Build a portfolio-grade, multi-tenant, AI-native manufacturing ERP for small and medium-sized manufacturers and distributors. The platform should connect sales, procurement, inventory, manufacturing, quality, finance, assets, workforce operations, analytics, and AI-assisted decision making in one coherent system.
2. Portfolio Objective
The project must demonstrate full-stack engineering, enterprise backend architecture, relational database design, security, event-driven systems, AI agents, retrieval-augmented generation, predictive machine learning, testing, observability, and deployment.
Demonstrate advanced Next.js/React/TypeScript frontend engineering.
Demonstrate Spring Boot enterprise backend engineering while leveraging the developer's existing Node.js experience.
Demonstrate PostgreSQL expertise beyond basic CRUD.
Demonstrate AI integration as a business capability rather than as a standalone chatbot.
Demonstrate production-minded architecture without prematurely decomposing everything into microservices.

5. Key End-to-End Workflows
1.Lead → opportunity → quotation → sales order → inventory reservation → delivery → invoice → payment → accounting entries.
2.Purchase requisition → approval → RFQ → supplier selection → purchase order → receipt → inventory update → supplier invoice → AP entry.
3.Demand → MRP planning → planned purchase/production order → material allocation → production → quality inspection → finished goods → inventory.
4.Customer return → inspection → accepted/rejected disposition → inventory adjustment → credit note → accounting.
5.AI recommendation → permission check → proposed action → human approval where required → transactional execution → audit event.
6. Accounting Requirements
Implement simplified but real double-entry accounting. Business actions that have financial impact must produce traceable journal entries.
Immutable or append-only accounting journal records.
Balanced debit/credit entries.
Chart of accounts and account types.
Accounting periods and period closing controls.
Accounts receivable and payable.
Trial balance, profit and loss, and balance sheet reports.
Clear source-document references from financial entries back to invoices, payments, receipts, or other business events.
7. Inventory Requirements
Maintain an inventory transaction ledger rather than relying only on a mutable quantity field.
Support receipts, issues, transfers, reservations, adjustments, production consumption, production output, returns, batch/lot and serial tracking.
Make stock-changing operations transactional and auditable.
Support reorder points and safety stock.
Implement a defined inventory valuation strategy; the initial release may use weighted average, with FIFO designed as an extension.
8. Manufacturing Requirements
BOMs with component quantities and units of measure.
Versioned BOMs and effective dates.
Routings and work centers.
Production order lifecycle: planned → released → in progress → quality → completed/cancelled.
Material reservation and consumption.
Finished-goods receipt.
Scrap and yield tracking.
Basic capacity and material availability checks.
9. AI Product Requirements
ERP Copilot for natural-language analytics and operational questions.
Tool-calling AI agent that can query ERP data through permission-aware tools.
Human-in-the-loop approval for high-impact write actions.
RAG over company policies, SOPs, manuals and product documentation using PostgreSQL/pgvector initially.
Demand forecasting using historical ERP data.
Anomaly detection for procurement, expenses, inventory shrinkage and unusual operational behavior.
AI-generated explanations must distinguish source facts, calculations, predictions and uncertainty.
All AI actions and important tool calls must be auditable.
10. Non-Functional Requirements
Security: tenant isolation, RBAC, backend authorization, secure secrets, rate limiting and audit logs.
Reliability: transactional integrity, idempotent event consumers, retries and dead-letter handling.
Performance: pagination, indexing, caching where justified, asynchronous processing for long-running jobs.
Observability: structured logs, metrics, traces and correlation IDs.
Accessibility: keyboard navigation, semantic HTML, visible focus states and appropriate ARIA usage.
Testing: unit, integration, API, end-to-end and selected contract/event tests.
Documentation: setup guide, architecture diagram, API documentation, ADRs and AI behavior documentation.

12. Definition of Done
Feature works through the UI and API where applicable.
Authorization rules are enforced server-side.
Database migrations are included.
Validation and error handling are implemented.
Tests cover business-critical paths.
Logs and audit events exist for important state changes.
API documentation is updated.
No secrets are committed.
Lint/type/build/test checks pass.
The implementation is documented enough for another engineer to run and understand.
AI Agent Operating Instructions
6.Act as a senior staff-level engineer. Do not blindly generate code; first inspect the repository, current dependency versions, architecture, existing conventions, and tests.
7.Before adding or upgrading any dependency, verify the latest stable production release from the official project documentation or package registry. Never select a beta, release candidate, nightly, deprecated, or end-of-life version unless the specification explicitly requires it.
8.Prefer stable, well-supported modules and official integrations. Do not introduce a library merely because it is popular if the platform already provides the required capability.
9.Preserve existing working behavior. Make incremental, reviewable changes and avoid unrelated refactors.
10.Before implementing a major feature, write a short implementation plan, identify affected modules, data changes, API changes, security implications, and tests.
11.Use strong typing, validation, explicit error handling, structured logging, and clear domain boundaries.
12.Never place secrets, API keys, credentials, tokens, or private customer data in source code, commits, logs, screenshots, fixtures, or generated documentation.
13.Do not invent APIs, framework features, configuration keys, database columns, or package names. Verify them against current official documentation.
14.Do not silently change the architecture. If a requested implementation conflicts with the architecture, explain the conflict and choose the least disruptive compatible approach.
15.After each meaningful implementation unit, run formatting, static analysis, unit tests, integration tests relevant to the change, and build checks. Fix failures before continuing.
16.For database changes, use migrations. Never modify production schema manually or rely on auto-generated destructive schema updates.
17.For security-sensitive operations, default to deny. Enforce authorization on the backend; frontend checks are only for UX.
18.For AI-generated actions that can mutate ERP state, require explicit permission checks and configurable human approval for high-impact operations.
19.Document important architectural decisions and trade-offs in ADRs or equivalent project documentation.
20.Keep the project portfolio-quality: readable code, coherent naming, tests, documentation, observability, reproducible local setup, and production-minded defaults.
